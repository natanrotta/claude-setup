# Finish — PR creation

You commit, push, and open a pull request against the base branch configured in `.claude/patterns/BASELINE.md` (typically `develop` or `main`).

This skill assumes the work is already implemented and validated. It does **not** run tests or code review — that's `/finish-task`'s job. Direct invocation of `/finish` is for cases where the user has already validated locally and wants to skip the gates.

---

## Steps

### 1. Preflight

- Run `git status`. If clean → abort with "Nothing to finish."
- Run `git branch --show-current`. If on the base branch → abort.
- Read BASELINE for the **base branch** name.

### 2. Commit (if there are uncommitted changes)

Inspect staged + unstaged changes. Draft a conventional-commit message:

```
<type>(<scope>): <summary>

<optional body>
```

- `type`: `feat`, `fix`, `chore`, `refactor`, `test`, `docs`, `perf`
- `scope`: the module name (if applicable)
- `summary`: under 70 characters, imperative ("add", "fix", not "added", "fixes")

Stage the relevant files (prefer specific paths over `git add .`). Commit via HEREDOC so the message preserves formatting.

Do **not** include a marketing footer ("Generated by AI", emojis, etc.) unless the project's commit convention requires it.

### 3. Push

```bash
git push -u origin <branch>
```

If the push is rejected (e.g., upstream rebase), report the error and stop. Do not force-push unless the user explicitly asks.

### 4. Open the PR

Use `gh pr create`. The PR title mirrors the commit message summary; the body follows this template:

```markdown
## Summary
<1-3 bullets describing what changed and why>

## Test plan
- [bulleted checklist of how to manually verify]

## Related
<ticket link or "n/a">
```

If the project has a `pull_request_template.md` in `.github/`, prefer that template's structure and fill the sections from conversation context.

Target branch: the BASELINE-configured base branch.

### 5. Optional: ticket integration

If BASELINE § Integrations lists a ticket tracker (Jira, Linear, GitHub Issues, etc.):

- Comment the PR URL on the ticket.
- Transition the ticket status to the configured value (e.g., "In Review").

If no integration is configured, skip this step silently.

### 6. Report

Return the PR URL and a one-line summary.

---

## Hard rules

1. **Never `git push --force` to a shared branch** unless the user explicitly asks.
2. **Never use `--no-verify`** to skip pre-commit hooks.
3. **Never commit secrets.** Reject any commit that includes `.env`, credentials, API keys.
4. **Use HEREDOC for commit messages** so newlines and special characters are preserved.
